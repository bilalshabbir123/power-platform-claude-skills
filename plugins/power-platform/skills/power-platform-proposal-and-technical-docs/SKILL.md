# Client proposals and technical documents (Word)

## Purpose
- **What it does:** a repeatable way to write and check client-facing documents (proposal, reissued proposal, technical build summary, handover notes) so every number agrees, every claim is true for the product and plan being sold, and a non-technical reader understands it on the first read.
- **When to use it:** before sending any proposal or RfP response; when the client changes direction (e.g. from an Azure / Power Pages build to a Microsoft 365 + Claude approach) and the proposal must be reissued; when asked for a short technical summary or a "simple words" rewrite.
- **Expected outcome:** a .docx that passes the checklist below, generated by a script kept next to it so v0.2 is a quick edit, and a short list of open points (prices, client confirmations) shown as `[TBC]` rather than guessed.

## Expertise
- **Bid managers** read the RfP first and turn every "must" into a row of a compliance table: requirement / where we answer it / status.
- **Architects** check each technical claim against the plan or licence actually being sold, not the best tier of the product (audit logs, data residency, group targeting are often top-tier only).
- **Consultants** write for the business owner: short sentences, the client's own words, one idea per row, an example where a step is abstract.
- **Field-tested practice:** one table of "what we build" with days per row, summed by formula or script, is read more than any other part of the document - so it must be right.

## Instructions

### Design approach
1. **Read everything first, in this order:** the RfP (deadlines, mandatory sections, price format, constraints), the last proposal sent, then meeting notes and emails since. Note every number (users, documents, checklist items, contracts, weeks, days, prices) with where it appears.
2. **Build a facts sheet** before writing: one value per quantity, with its source. Every later section uses only these values.
3. **Pick the document type and keep it to its job:**
   | Document | Length | Contains |
   |---|---|---|
   | Proposal / reissued proposal | as the RfP asks | scope, approach, deliverables, plan, team, prices (by phase), assumptions, exclusions, compliance table |
   | Technical build summary | 2-3 pages | what we build (table with days), set-up, components (skills, flows, lists, plugin, commands), testing, options - **nothing else** |
   | Handover | as needed | where things are, what's done, what's pending, how to roll back |
4. **When the approach changes,** rewrite from the facts sheet; don't patch the old document. Leftovers from the old approach (licences, service accounts, "exclusively Microsoft" claims) are the most common error.
5. **Unknowns are visible:** prices `[£TBC]`, client confirmations as numbered questions with our suggestion. Never ship `£00,000` or invented figures.

### Development standards (writing)
- Plain English: "Claude can read SharePoint but cannot write to it" beats "read-only delegated connector scope". If a step is abstract, add a one-line example.
- One main table of components: **Component | What it is | What we do | Days**. Merge rows that describe the same thing (e.g. "Knowledge Vault" and "Knowledge Catalogue"; "Forms", "Lists" and "Flows").
- Don't oversell: "assisted review" not "automated review"; "labelled AI suggestions" not "AI recommendations"; no "audit compliance" if the plan has no audit log; no legal advice.
- Label every AI output in the design: e.g. "AI DRAFT - engineer review required"; a person approves anything that is published.
- Number sections automatically or check every "see section N" after any insert.

### Development standards (generating the .docx)
- Generate with a script (e.g. `docx` npm, pinned version) kept next to the output; never hand-edit the generated file and the script separately.
- Set the font on **every run** and on the Normal style; otherwise Word falls back to Times New Roman for runs without a font.
- A4: page 11906 x 16838 twips; tables with fixed layout, widths in DXA, header row repeated, rows that can't split, alternate row shading for long tables.
- Use a common font (Arial/Calibri) in the document; brand fonts go in images only.
- After writing, remove the ZIP folder entries: `zip -d out.docx '*/'` - Word has refused files that contain them when opened through a cloud co-editing service.
- **Check the page count in Word itself** (export to PDF and count pages), not a previewer: Quick Look and other renderers paginate differently.
  ```bash
  # macOS: Word only writes inside its sandbox container
  cp out.docx ~/Library/Containers/com.microsoft.Word/Data/Documents/
  osascript -e 'tell application "Microsoft Word"' -e 'open POSIX file "'$HOME'/Library/Containers/com.microsoft.Word/Data/Documents/out.docx"' \
    -e 'save as active document file name "out.pdf" file format format PDF' -e 'close active document saving no' -e 'end tell'
  pdfinfo ~/Library/Containers/com.microsoft.Word/Data/Documents/out.pdf | grep Pages
  ```

### Governance and DLP
- Client documents, transcripts and drafts stay in the client's project folder (OneDrive/SharePoint), **never** in a public repo. Only anonymised lessons go to shared skill repos.
- State which provider processes the data and where it is stored. If the RfP asked for UK/EU residency and the proposed product doesn't offer it on that plan, say so and ask the client to accept it in writing (with the vendor's confirmation reference and date).
- List the human approvals: who approves knowledge updates, who releases a skill/app, who owns each document.

### Security
- No tenant IDs, environment URLs, emails or service-account passwords in the document.
- Remove prerequisites that weaken security (e.g. "service account without MFA") or justify them and add the compensating control.
- Say exactly what each component can access ("searches only what the signed-in user can already open") and what limits it can't enforce (e.g. a connector that searches the whole tenant can be told, not forced, to use one site - add an oversharing check).

### Performance
- Keep to the page limit the client set; cut background, not facts. A 3-page technical summary has no marketing, no team bios, no company history.
- State volumes the design was sized for (users, documents, contracts) - the same numbers everywhere.

### ALM
- Version on the cover (v0.1 draft, v1.0 issued), date, validity period, "DRAFT" in the filename until issued.
- Keep the generator script and a text export of the previous issue so differences can be listed in a change note.

### Licensing
- Name the licence or plan per user for every component and check top-tier-only features against the plan sold (e.g. Claude Team vs Enterprise: audit logs, compliance API, group targeting; Power Automate standard vs premium connectors).
- Prefer standard connectors (SharePoint, Forms, Approvals, Teams, Outlook) where they are enough, and say so - it removes a licence cost.
- Running costs: one table, per month, with what's included; the same figures wherever they appear.

## Examples

### Beginner
Asked for "a technical summary, max 3 pages": sections = what we build (table with days and total) / set-up / components / testing / options. Generate, export to PDF from Word, confirm 3 pages.

### Intermediate
Reviewing a proposal before sending: the facts sheet shows "100 documents" in scope and "20 documents" in the plan, "5 users" vs "10 users", and Phase B rows adding to 9.5 days against a stated 17. Report each with page and section, pick one value with the author, fix all occurrences.

### Advanced (enterprise)
Client switches from a custom Azure build to Microsoft 365 + Claude Team. Reissue: rewrite scope from the facts sheet; remove the Copilot Studio licence and Azure running costs; add the data-residency position with the vendor's written confirmation; explain how learning gets back into SharePoint without Claude writing to it (pre-filled Microsoft Forms link → Power Automate approval → owner publishes); list Enterprise-only features the plan doesn't have and the workaround for each (e.g. test pack and a scorecard list instead of audit logs).

## Common mistakes
| Mistake | What happens | How to avoid |
|---|---|---|
| Placeholder prices left in (`£00,000`) | Client sees an unfinished document | `[£TBC]` and a pre-send search for `00,000`, `TBC`, `XX` |
| Same quantity with different values | Client doubts every number | Facts sheet; search each number before sending |
| Day rows don't add up to the stated total | Price looks padded or careless | Sum in the script / a formula, print the total from it |
| Client effort stated as hours next to days of ours | Looks unrealistic | Same unit, a row per client activity |
| Old-approach leftovers (licences, service accounts, "exclusively Microsoft") | Contradicts the new scope | Rewrite from the facts sheet; search old product names |
| Claiming features of a higher plan (audit logs, residency) | Broken promise found in security review | Check each claim against the plan sold; label [Microsoft]/[Vendor] with a link |
| Jargon the reader can't follow | Repeated "I don't understand" rounds | Plain words, one example per abstract step, short rows |
| Duplicate testimonial, typos in client/partner names | Looks careless | Read names aloud; search duplicates |
| "See section 13" after inserting a section | Wrong cross-references | Auto-numbering or a final cross-reference check |
| Body text in Times New Roman | Unprofessional look | Font on every run and the Normal style |
| Page count checked in a previewer | Over the limit in Word | Export to PDF from Word and count |
| Overselling AI ("automated", "recommendations") | Liability, failed trust | "assisted", "labelled AI suggestions", human approval |

## Validation checklist

### Security
- [ ] No tenant IDs, URLs, emails, passwords or real customer data
- [ ] No security-weakening prerequisite without a compensating control
- [ ] Access limits described truthfully, including what can't be enforced
### Performance
- [ ] Within the page limit, checked by Word PDF export
- [ ] Every quantity has one value across the document
### ALM
- [ ] Version, date, validity on the cover; DRAFT in the filename until issued
- [ ] Generator script saved next to the .docx
### Solution packaging
- [ ] Component table merged and summed; total matches the plan and the price
- [ ] Prices split as the RfP requires (e.g. by phase and support, currency, VAT basis)
### Deployment readiness
- [ ] Every RfP "must" appears in the compliance table
- [ ] Data processing location and provider stated; client acceptance requested where it differs from the RfP
- [ ] Licence/plan named for every component; top-tier-only features checked
- [ ] Pre-send search: `00,000`, `TBC`, `XX`, old product names, duplicate paragraphs

## Troubleshooting
| Symptom | Likely cause | Fix |
|---|---|---|
| Some text in Times New Roman | Runs created without a font | Helper that sets font/size on every run + Normal style |
| Word says the file can't be opened (cloud) | ZIP folder entries | `zip -d out.docx '*/'` |
| PDF export fails silently on macOS | File outside Word's sandbox | Copy into `~/Library/Containers/com.microsoft.Word/Data/Documents/` |
| Table columns squashed | Auto layout / percentage widths | Fixed layout, DXA widths summing to the text width |
| Validation script won't run | Old system Python | Use a current Python or skip and open in Word to check |
